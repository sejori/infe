# 01 — How inference engines declare serving configuration, and whether any cross-engine abstraction exists

Research date: 2026-09-03. Method: official docs, GitHub repos and release notes fetched live; platform survey (section 5) delegated to three parallel research agents and merged here. Anything marked **[unverified]** could not be confirmed from a primary source.

Caveat on dates: the fetch tooling rendered several GitHub release dates with the wrong year (e.g. vLLM v0.28.0 "26 Aug" carrying PR numbers in the #49k–#52k range, which is unambiguously 2026). Years below are inferred from version sequence and PR numbers where the rendered year was implausible; day/month values are as rendered.

---

## 1. One-page summary

| Engine | Primary config surface | File-based config? | Env-var mirror? | Typed schema behind it | Surface stability (12 mo) | Recipe ecosystem |
|---|---|---|---|---|---|---|
| vLLM | `vllm serve` CLI (argparse generated from `vllm.config` dataclasses) | Yes: `--config x.yaml` (keys = long CLI names) | Partial (`VLLM_*` env vars, being migrated *to* CLI flags) | Yes: `EngineArgs` → `VllmConfig` (ModelConfig, ParallelConfig, CacheConfig, SchedulerConfig, SpeculativeConfig, LoRAConfig, StructuredOutputsConfig, CompilationConfig …) | Low-medium. Formal 2-minor-release deprecation policy, but ~2 minor releases/month in 2026 and a steady stream of removals | `vllm-project/recipes` (structured YAML + JSON API + `tools/recipes` converter) |
| SGLang | `python -m sglang.launch_server` / `sglang serve` CLI | Yes: `--config x.yaml` (meta-arg) | No systematic mirror (some `SGLANG_*` feature env vars) | Yes: `ServerArgs` dataclass (~280+ fields) | Low. Renames shipped **without** aliases in v0.5.16; DeprecatedAction aliases exist for some others; docs lag the code | `sgl-project/sgl-cookbook` (YAML model configs → React "ConfigGenerator" → CLI string) |
| TensorRT-LLM | `trtllm-serve` CLI + YAML for `LlmArgs` (`--config`, alias `--extra_llm_api_options`) | Yes (nested YAML mirroring `TorchLlmArgs`) | No | Yes: Pydantic `LlmArgs`/`TorchLlmArgs`, fields tagged `stable`/`beta`/`prototype` | Medium. Field-level stability tags; PyTorch backend default; `trtllm-build` TensorRT path now "legacy" | NVIDIA "Deployment Guides / Quick Start Recipes" (per model × Blackwell/Hopper) |
| llama.cpp `llama-server` | CLI flags | Router-mode `.ini` presets (`--models-preset`) since Dec 2025 | Yes: every flag has `LLAMA_ARG_*` | `common_params` C++ struct | Medium. Flags fairly stable; new router mode added | HF blog/model cards; no central recipe repo |
| Ollama | Modelfile (`FROM/PARAMETER/TEMPLATE/SYSTEM/ADAPTER`) | The Modelfile *is* the file | `OLLAMA_*` for server-level only | Yes (small, fixed PARAMETER list) | High (deliberately small surface) | Model library is the preset ecosystem |
| LMDeploy | `lmdeploy serve api_server` CLI; `TurbomindEngineConfig` / `PytorchEngineConfig` Python classes | Not found | No | Yes (two divergent dataclasses, one per backend) | Medium | None notable |
| TGI (HF) | `text-generation-launcher` CLI | No | Yes: every flag has an UPPER_SNAKE env var | Rust clap struct | Frozen — maintenance mode 2025-11-12, **repo archived 2026-03-21** (v3.3.7 final) | n/a |
| MLC-LLM | `mlc-chat-config.json` (generated at compile time) + `mlc_llm serve --overrides` | The JSON *is* the config | No | Yes (compile-time vs runtime split) | Medium-low; low activity (~30 commits / 3 mo) | Pre-built HF model libs |
| Modular MAX | `max serve` CLI | `--config-file` (format undocumented) | No | Yes (Python `PipelineConfig`) | Medium; versioned docs (v26.5) | Model "builds" list |
| Aphrodite → **Sonar** | `aphrodite serve` CLI (vLLM-derived) | `aphrodite yaml config.yaml` (sectioned YAML, not flat CLI names) | inherits vLLM's | vLLM's, plus additions | Tracks vLLM main by sha-sync; rebranded "Sonar" in v0.22.0 (Jul 2026) | none |
| exllamav2/v3 via TabbyAPI | `config.yml` (sectioned YAML) | Yes, it is the primary surface | No | Pydantic models per section | Medium; v3 replacing v2 with different fields | none |

**Headline:** every engine exposes a *flat-ish, engine-specific* option list. Only Ollama's Modelfile and TabbyAPI's `config.yml` are "config-file-first" designs; everything else is CLI-first with YAML as an alternate encoding of the same flag names. No engine ships a config-migration tool between its own versions; deprecation is handled (where at all) by runtime warnings/aliases.

## 2. Per-engine detail

### 2.1 vLLM

**Config format.** `vllm serve <model> [flags]`. Flags are auto-generated from the dataclasses in `vllm.config` (`ModelConfig`, `LoadConfig`, `ParallelConfig`, `CacheConfig`, `SchedulerConfig`, `SpeculativeConfig`, `LoRAConfig`, `StructuredOutputsConfig`, `CompilationConfig`, `ObservabilityConfig`, `OffloadConfig`, `MultiModalConfig`, `AttentionConfig`, `MambaConfig`, `KVTransferConfig`). Composite configs accept JSON *or* dotted keys: `--compilation-config '{"level":3}'` or `--compilation-config.level 3`; list append via `--json-arg.key4+ value`. Source: https://docs.vllm.ai/en/latest/configuration/engine_args/

YAML: `vllm serve MODEL --config config.yaml`; keys must be the long-form flag names (hyphenated), precedence `command line > config file > defaults`; positional model on the CLI beats the file. Source: https://docs.vllm.ai/en/latest/configuration/serve_args/

**Notable dimensions (exact flags, latest docs):**
- Parallelism: `--tensor-parallel-size/-tp`, `--pipeline-parallel-size/-pp`, `--data-parallel-size/-dp`, `--enable-expert-parallel/-ep` (boolean, not a size), `--prefill-context-parallel-size/-pcp`, `--decode-context-parallel-size/-dcp`, `--distributed-executor-backend {ray,mp,external_launcher,uni}`.
- Quantisation: `--quantization/-q`, `--dtype`, `--kv-cache-dtype {auto,bfloat16,float16,fp8,nvfp4,…}`.
- KV / memory: `--gpu-memory-utilization` (default 0.92 now), `--kv-cache-memory-bytes`, `--block-size`, `--max-model-len` (accepts `25.6k`/`auto`), `--enable-prefix-caching`, `--prefix-caching-hash-algo`, `--cpu-offload-gb`, `--watermark`.
- Scheduler: `--max-num-seqs`, `--max-num-batched-tokens`, `--max-num-queued-reqs`, `--scheduling-policy {fcfs,priority}`, `--enable-chunked-prefill`, `--async-scheduling` (default on), `--stream-interval`.
- Speculative: single JSON blob `--speculative-config '{"method":"eagle3",…}'`.
- LoRA: `--enable-lora`, `--max-loras`, `--max-lora-rank`, `--lora-dtype`.
- Structured output: `--structured-outputs-config` (backend etc.), `--reasoning-parser`, `--reasoning-parser-plugin`.
- Compile/attention: `--compilation-config`, `--cudagraph-capture-sizes`, `--attention-backend` (replaces the `VLLM_ATTENTION_BACKEND` env var since v0.13.0).
- Escape hatches: `--hf-overrides`, `--override-generation-config`, `--model-impl {auto,vllm,transformers,terratorch}`.

**Stability.** Formal deprecation policy: deprecate in Y → off-by-default in Y+1 → remove in Y+2; removals only in minor (Y) releases; notices in help strings, logs, `/metrics`, release notes. It explicitly covers "CLI flags, environment variables, configuration files" but has no config-migration guidance. Source: https://docs.vllm.ai/en/latest/contributing/deprecation_policy/. In practice the cadence is now roughly two minor releases per month (v0.26.0 27 Jul 2026, v0.27.0 10 Aug, v0.27.1 11 Aug, v0.28.0 26 Aug 2026 — https://github.com/vllm-project/vllm/releases), so "two minors" can be under six weeks of wall-clock time. Concrete rename/removal history is in section 3.

**Recipes.** https://github.com/vllm-project/recipes — structured YAML at `models/<hf_org>/<hf_repo>.yaml`, rendered as an interactive command builder at recipes.vllm.ai and exported as JSON "for agent consumption". Schema (CONTRIBUTING.md): `meta` (title/slug/provider/difficulty/tasks/hardware verification), `model` (`model_id`, `min_vllm_version`, `docker_image`, `architecture: dense|moe`, `parameter_count`, `context_length`, `base_args`, `base_env`), `features` / `opt_in_features` (each with CLI args), `variants` (precision `bf16|fp8|nvfp4|int4…`, `vram_minimum_gb = ceil(params × bytes_per_param × 1.2)`), `compatible_strategies` from a `strategies/*.yaml` registry (`single_node_tp`, `single_node_tep`, `single_node_dep`, `multi_node_tp`, `multi_node_tp_pp`, `pd_cluster`), `hardware_overrides` (Hopper/Blackwell/AMD extra args+env), `strategy_overrides`, `nightly_required`, `dependencies`. Source: https://github.com/vllm-project/recipes/blob/main/CONTRIBUTING.md. The vLLM repo itself ships `tools/recipes/recipe_json_to_vllm_config.py` that turns a recipe rendering into `config.yml` + `env.sh`, optionally refines `tensor-parallel-size` / `gpu-memory-utilization` from detected hardware, and can `--generate-sweep` for benchmark-backed tuning. Source: https://github.com/vllm-project/vllm/blob/main/tools/recipes/README.md. **This is the closest thing to a "typed intent → engine flags" compiler that exists today, but it is vLLM-only.**

### 2.2 SGLang

**Config format.** `python -m sglang.launch_server --model-path … [flags]` (also `sglang serve`). Backing type: `ServerArgs` dataclass in `python/sglang/srt/server_args.py`, roughly 280+ fields. YAML config via `--config` ("CLI arguments will override config file values"). Sources: https://docs.sglang.io/docs/advanced_features/server_arguments ; https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/server_args.py

**Notable dimensions:**
- Parallelism: `--tp-size` (alias `--tensor-parallel-size`, `--tp`), `--pp-size`, `--dp-size`, `--ep-size`, `--enable-dp-attention`, plus fine-grained `--attn-tp-size`, `--attn-dp-size`, `--moe-tp-size`, `--moe-dp-size`, `--moe-ep-size`, `--attention-context-parallel-size/--attn-cp-size`, `--dcp-size`, `--moe-a2a-backend {none,deepep,mooncake,nixl,mori,…}`. Note the semantics of `--tp-size`/`--dp-size` *change* when `--enable-dp-attention` is set — an acknowledged design wart (issue #8530 "Brainstorm: refactor parallel sizes", opened Jul 2025, closed inactive: https://github.com/sgl-project/sglang/issues/8530).
- Quantisation: `--quantization`, `--dtype`, `--kv-cache-dtype {auto,fp8_e5m2,fp8_e4m3,bf16,nvfp4,fp4_mx_block16}`.
- KV / memory: `--mem-fraction-static`, `--max-total-tokens`, `--page-size`, `--disable-radix-cache`, `--hicache-*` (hierarchical cache), `--chunked-prefill-size`.
- Scheduler: `--max-running-requests`, `--schedule-policy {fcfs,lpm,random,lof,priority,routing-key}`, `--schedule-conservativeness`.
- Speculative: `--speculative-algorithm {EAGLE,STANDALONE,NGRAM}`, `--speculative-draft-model-path`, `--speculative-num-steps`, `--speculative-eagle-topk`, `--speculative-num-draft-tokens`.
- LoRA: `--enable-lora`, `--lora-paths name=/path …`, `--max-loras-per-batch`, `--max-lora-rank`, `--lora-backend {triton,csgmv,torch_native}`.
- Structured output: `--grammar-backend {xgrammar,outlines,llguidance,none}`, `--constrained-json-whitespace-pattern`, `--reasoning-parser`, `--tool-call-parser`.
- Attention: `--attention-backend {triton,torch_native,flex_attention,dsa,nsa,dsv4,cutlass_mla,fa3,fa4,flashinfer,…}`.

**Stability.** `server_args.py` imports `DeprecatedAction`, `DeprecatedAliasStoreAction`, `DeprecatedStoreConstAction`, `DeprecatedStoreTrueAction` and uses them for some renames (`--nccl-init-addr` → `--dist-init-addr`, `--grpc-mode` → `--smg-grpc-mode`, `--grpc-http-sidecar-port` → `--smg-http-sidecar-port`), but v0.5.16 renamed flags **with no alias at all** (see section 3). Docs demonstrably lag code: discussion #14310 (2 Dec 2025, unanswered) reports the server-args page missing newly added args despite a doc-sync bot: https://github.com/sgl-project/sglang/discussions/14310. Release cadence ≈ every 2 weeks (v0.5.13 … v0.5.18 between mid-Jun and 22 Aug 2026; v0.5.18 alone was 710 PRs): https://github.com/sgl-project/sglang/releases

**Recipes.** https://github.com/sgl-project/sgl-cookbook (site: cookbook.sglang.io). Human-edited YAML in `data/models/src/<version>/` is compiled to schema-compliant YAML in `data/models/generated/<version>/`; fields include company-wide defaults (`tp`, `dp`, `ep`, `enable_dp_attention`), variant generation from `base_name` × quantisations × capabilities, per-hardware `tp/dp/ep` overrides, and FP8/BF16 overrides. A React `ConfigGenerator` component per model turns UI selections into a CLI string. Source: https://github.com/sgl-project/sgl-cookbook/blob/main/CLAUDE.md. Structurally similar to vLLM recipes (typed → flags) but a different schema, different rendering, and SGLang-only.

### 2.3 TensorRT-LLM

**Config format.** Two layers. (a) `trtllm-serve <model>` CLI with a *small* set of top-level flags: `--backend {pytorch,_autodeploy}` (pytorch is default), `--tp_size/--tensor_parallel_size`, `--pp_size`, `--ep_size/--moe_expert_parallel_size`, `--max_batch_size`, `--max_num_tokens`, `--max_seq_len`, `--kv_cache_free_gpu_memory_fraction`, `--trust_remote_code`, `--reasoning_parser`, `--tool_parser`, `--disagg_cluster_uri`, `--num_postprocess_workers`. (b) Everything else via YAML: `--config file.yaml` ("preferred"; `--extra_llm_api_options` remains "an equivalent alias", documented as a *non-breaking* rename) which populates `tensorrt_llm.llmapi.LlmArgs` / `TorchLlmArgs`, nested keys as hierarchy (`moe_config.backend: CUTLASS`). CLI flags override YAML. Source: https://nvidia.github.io/TensorRT-LLM/commands/trtllm-serve/trtllm-serve.html

**Notable dimensions (LlmArgs fields, each tagged with a stability level in the API reference):** `tensor_parallel_size`, `pipeline_parallel_size`, `context_parallel_size`, `moe_tensor_parallel_size`, `moe_expert_parallel_size` (stable); `enable_attention_dp` (beta); `max_batch_size` (default 2048), `max_num_tokens` (default 8192), `max_seq_len`, `max_input_len`, `max_beam_width` (stable); `kv_cache_config` {`free_gpu_memory_fraction`, `dtype`, `enable_block_reuse`} (stable); `quant_config`; `speculative_config` {`decoding_type`: MTP / Eagle3 / NGram / DraftTarget …} (stable); `guided_decoding_backend {xgrammar,llguidance}` (stable); `lora_config` (stable), `peft_cache_config` (prototype); `scheduler_config` (prototype), `cuda_graph_config` (beta), `attn_backend` (beta), `moe_config` (beta), `disable_overlap_scheduler` (beta), `cache_transceiver_config` (prototype). Source: https://nvidia.github.io/TensorRT-LLM/llm-api/reference.html. **TRT-LLM is the only engine that tags individual config fields with a stability level** — useful signal for a porting tool.

**Build configs.** The older TensorRT-engine path (`trtllm-build --checkpoint_dir … --max_batch_size --max_input_len --max_seq_len --max_num_tokens --gemm_plugin --use_paged_context_fmha --kv_cache_type {continuous,paged,disabled} --lora_plugin --speculative_decoding_mode`) bakes many of these choices into a compiled engine; the docs now describe the TensorRT engine path as "legacy" with the PyTorch backend as default. Source: https://nvidia.github.io/TensorRT-LLM/commands/trtllm-build.html. Implication: for TRT-LLM "config" can be a build-time artefact, not just a launch-time one.

**Recipes.** NVIDIA "Deployment Guides" = quick-start recipes per model × hardware (Nemotron v3, DeepSeek R1, Llama 3.3 70B, Llama 4 Scout, GPT-OSS, Qwen3 / Qwen3.5-MoE / Qwen3.8-MoE, Kimi K2 Thinking, Kimi K3, GLM-5, MiniMax-M3), each with a "recipe selector" for aggregated (in-flight batched) serving and max ISL/OSL tables; they provide an `extra-llm-api-config.yml` and a `trtllm-serve` command. Version pinning is by docs build ("generated by commit 785c948"), not by a field in the recipe **[partially verified — recipe file contents not inspected]**. Source: https://nvidia.github.io/TensorRT-LLM/deployment-guide/index.html

### 2.4 llama.cpp / `llama-server`

**Config format.** CLI flags; *every* flag has an env-var twin with the `LLAMA_ARG_` prefix (CLI wins). No config file for a single model. Since Dec 2025, **router mode**: start `llama-server` without `-m` and it becomes a proxy that spawns child processes per model; `--models-dir`, `--models-max N` (default 4), `--models-autoload/--no-models-autoload`, and `--models-preset FILE.ini` where each `[section]` is a model id and keys mirror CLI long names (e.g. `model = /path.gguf`, `ctx-size = 65536`, `temp = 0.7`). Sources: https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md ; https://huggingface.co/blog/ggml-org/model-management-in-llamacpp (11 Dec 2025). A global `[*]` defaults section and `load-on-startup` / `stop-timeout` keys are described by third-party write-ups but **[unverified in the README]**.

**Notable dimensions:** context `-c/--ctx-size`; offload `-ngl/--gpu-layers`, `-sm/--split-mode {none,layer,row,tensor}`, `-ts/--tensor-split`; batching `-b/--batch-size` (2048), `-ub/--ubatch-size` (512), `-np/--parallel` (slots, `-1`=auto); KV `-ctk/--cache-type-k`, `-ctv/--cache-type-v` (f16/bf16/q8_0/q4_0…), `-fa/--flash-attn`; LoRA `--lora`, `--lora-scaled`; speculative `-md/--model-draft`, `--spec-draft-n-max` (3), `--spec-draft-n-min`; constraints `--grammar`, `--json-schema`. Runtime introspection via `/props` and `/slots`. Note the vocabulary is quite different from GPU engines: no TP/PP/DP/EP as such (multi-GPU is "split mode"), "quantisation" is a property of the GGUF file rather than a flag, and there is no scheduler policy knob.

### 2.5 Ollama

**Config format.** The Modelfile. Valid instructions per `parser.go`: `FROM`, `LICENSE`, `TEMPLATE`, `SYSTEM`, `ADAPTER`, `DRAFT` (speculative draft model), `RENDERER` (prompt renderer, e.g. `gemma4`, `qwen3-vl-instruct`), `PARSER` (thinking/tool-call parser, e.g. `harmony`, `qwen3-coder`, `passthrough`), `PARAMETER`, `MESSAGE`, `REQUIRES` (minimum Ollama version). Documented `PARAMETER`s: `num_ctx`, `repeat_last_n`, `repeat_penalty`, `temperature`, `seed`, `stop`, `num_predict`, `draft_num_predict`, `top_k`, `top_p`, `min_p`; the API `Runner` struct still accepts `num_batch`, `num_gpu`, `main_gpu`, `use_mmap`, `num_thread` (undocumented) while `use_mlock`, `mirostat`, `tfs_z` appear to have been dropped. Round-trip: `ollama show --modelfile <m>` → edit → `ollama create <name> -f Modelfile` (also imports safetensors with `-q Q4_K_M`). Sources: https://raw.githubusercontent.com/ollama/ollama/main/parser/parser.go ; https://raw.githubusercontent.com/ollama/ollama/main/api/types.go ; https://docs.ollama.com/modelfile

**Why it matters.** It is a genuine *model-level* abstraction (one small vocabulary for every model, round-trippable, versioned via `REQUIRES`) but is single-engine by design: Ollama now has three runtimes — the CGo llama.cpp runner, the pure-Go GGML "new engine" (issue #9959), and MLX on Apple Silicon (preview v0.19.0, 31 Mar 2026; now default there) — and **the Modelfile did not change**: engine selection is automatic per architecture/platform, there is no `ENGINE` instruction, and how `num_gpu` behaves on MLX is undocumented **[unverified]**. Sources: https://github.com/ollama/ollama/issues/9959 ; https://github.com/ollama/ollama/releases/tag/v0.19.0 ; https://ollama.com/blog/mlx. Server-level knobs (`OLLAMA_NUM_PARALLEL`, `OLLAMA_MAX_LOADED_MODELS`, `OLLAMA_FLASH_ATTENTION`, `OLLAMA_KV_CACHE_TYPE`) are env vars, outside the Modelfile.

### 2.6 LMDeploy

**Config format.** `lmdeploy serve api_server <model> --backend {turbomind,pytorch} [flags]`; programmatic equivalents are two *different* dataclasses, `TurbomindEngineConfig` and `PytorchEngineConfig`. No config-file option found in the docs. Sources: https://lmdeploy.readthedocs.io/en/latest/llm/api_server.html ; https://lmdeploy.readthedocs.io/en/latest/api/pipeline.html

**Notable dimensions:** shared — `tp`, `session_len`, `max_batch_size`, `cache_max_entry_count` (KV as fraction of free memory, default 0.8), `cache_block_seq_len`, `quant_policy` (KV int4/int8/fp8), `model_format` (hf/awq/gptq/fp8…), `enable_prefix_caching`, `max_prefill_token_num`, `hf_overrides`. Pytorch-only — `dp`, `dp_rank`, `ep`, `attn_tp_size`, `mlp_tp_size`, `moe_tp_size`, `enable_eplb`, `enable_microbatch`, `role {Hybrid,Prefill,Decode}`, `migration_backend`, `mp_engine_backend {mp,ray}`. Turbomind-only — `dtype`, `num_tokens_per_iter`, `max_prefill_iters`, `rope_scaling_factor`, `devices`. Speculative decoding (PyTorch backend): `--speculative-algorithm {eagle3,deepseek_mtp}`, `--speculative-draft-model`, `--speculative-num-draft-tokens` (https://lmdeploy.readthedocs.io/en/latest/advance/spec_decoding.html). LoRA via `--adapters`. Structured output: supported per docs index but the detail page 404'd **[unverified field names]**.

**Stability note:** the two backends *inside one engine* already have divergent config schemas — a mini-version of the cross-engine problem.

### 2.7 Text Generation Inference (Hugging Face)

**Status:** entered maintenance mode 2025-11-12; **repository archived (read-only) 2026-03-21**; last release v3.3.7. HF now points Inference Endpoints users at vLLM or SGLang. Sources: https://github.com/huggingface/text-generation-inference ; https://huggingface.co/docs/text-generation-inference/en/index

**Config format (frozen):** `text-generation-launcher` flags, each with an UPPER_SNAKE env var (`--num-shard`/`NUM_SHARD` = TP, `--quantize {awq,compressed-tensors,eetq,exl2,gptq,marlin,bitsandbytes*,fp8}`, `--dtype`, `--kv-cache-dtype {fp8_e4m3fn,fp8_e5m2}`, `--max-input-tokens` (legacy alias `--max-input-length`), `--max-total-tokens`, `--max-batch-prefill-tokens`, `--max-batch-total-tokens`, `--max-concurrent-requests`, `--cuda-graphs`, `--lora-adapters`, `--speculate N` (medusa/n-gram), `--disable-grammar-support`). Source: https://huggingface.co/docs/text-generation-inference/reference/launcher. Relevant to Robotnik only as a *migration source* (people still have TGI configs to port).

### 2.8 MLC-LLM

**Config format.** `mlc-chat-config.json`, generated by `mlc_llm gen_config` and consumed by `mlc_llm compile` and `mlc_llm serve`. Compile-time fields (`model_type`, `context_window_size`, `sliding_window_size`, `prefill_chunk_size`, `tensor_parallel_shards`, `vocab_size`, quantisation such as `q4f16_1`) are baked into the model library; the docs warn changing them at runtime "may lead to unexpected behavior". Runtime fields (`temperature`, `top_p`, `repetition_penalty`, `conv_template`) are overridable; `mlc_llm serve --overrides` accepts `tensor_parallel_shards`, `max_num_sequence`, `max_total_seq_length`, `prefill_chunk_size`, `gpu_memory_utilization`, `spec_draft_length`, `prefix_cache_max_num_recycling_seqs`, `context_window_size`, `sliding_window_size`, `attention_sink_size` (mapping to `EngineConfig` in `mlc_llm/serve/config.py`). Sources: https://llm.mlc.ai/docs/deploy/mlc_chat_config.html ; https://llm.mlc.ai/docs/compilation/compile_models.html

**Activity:** last commit 17 Aug 2026, ~30–35 commits in the prior three months, mostly TVM-API adaptation fixes (https://github.com/mlc-ai/mlc-llm/commits/main). Low priority target.

### 2.9 Modular MAX

**Config format.** `max serve --model-path … [flags]`, plus `--config-file` / `--draft-config-file` (listed but the file format is not documented on the CLI page). Flags: `--devices {cpu,gpu,gpu:all,gpu:0,1}`, `--device-memory-utilization`, `--data-parallel-degree`, `--quantization-encoding {float32,float16,bfloat16,q4_k,q4_0,q6_k,float8_e4m3fn,float4_e2m1fnx2,float6_e2m3fn,gptq}`, `--max-length`, `--max-batch-size`, `--kv-cache-page-size`, `--enable-prefix-caching`, `--enable-structured-output`, `--draft-model-path` + `--speculative-method {eagle,mtp,dflash}`, `--enable-lora` + `--lora-paths`, `--pipeline-role {prefill_and_decode,prefill_only,decode_only}`, `--use-experimental-kernels`. No tensor-parallel flag is listed on the serve page **[unverified whether TP is exposed elsewhere]**. Docs are versioned (nightly vs v26.5). Source: https://max.modular.com/cli/serve

### 2.10 Aphrodite Engine → "Sonar"

## 5. Is there any single config that targets multiple engines?

**Short answer: no.** Across 21 platforms surveyed, none ships a typed field that fans out to both `--tensor-parallel-size` (vLLM) and `--tp-size` (SGLang). The projects that *do* translate typed fields into flags translate into **vLLM only** (llm-d-modelservice chart, KServe `LLMInferenceService`, vLLM production-stack, KAITO). Everything else is an engine *selector* enum sitting above a raw `args`/`extraArgs`/`engine_kwargs`/env passthrough — which is not an abstraction.

Legend for the "Flags" column: **PT** = raw passthrough in the engine's own vocabulary; **T→vLLM** = typed fields rendered into vLLM flags only; **T-partitioned** = typed fields but each field belongs to one backend.

### 5.4 What *does* exist, in decreasing order of usefulness to Robotnik

1. **Typed intent → engine flags, single engine:** vLLM recipes + `tools/recipes` converter; sgl-cookbook config generators; NVIDIA TRT-LLM deployment guides; KAITO `configureParallelism` (SKU → TP/DP/PP); GPUStack's derived `--max-model-len`/`--tp-size`; llm-d-modelservice / KServe `parallelism.*` → vLLM.
2. **SLA/workload intent → generated deployment, multi-backend:** Dynamo `DynamoGraphDeploymentRequest` (`backend: auto|sglang|trtllm|vllm`, `sla`, `workload`). Only thing that spans engines, but by search, not by mapping.
3. **Engine + engine-version as first-class fields for the same model:** GPUStack (`backend`, `backend_version`, `version_configs.image_name`); Harbor `HARBOR_<SVC>_VERSION`; Jan `llamacpp_version`. Nobody has "same model, same intent, engine A vs engine B" as a diffable object.
4. **Capability matching (`can engine X serve format/quant Y?`):** Xinference `match_json()`; LocalAI gallery `variants`.
5. **Validated passthrough:** LocalAI `engine_args` checked against `AsyncEngineArgs` fields with suggestions — the cheapest safety net to copy.
6. **Cross-engine corpus of tuned configs:** SemiAnalysis InferenceX (vLLM/SGLang/TRT-LLM matrix, daily). Not an abstraction, but the best training data for one.

Field-name convergence that is *accidental* but exploitable: context length is `--max-model-len` (vLLM/Aphrodite/KAITO/production-stack) / `--context-length` (SGLang) / `max_seq_len` (TRT-LLM, TabbyAPI, MindIE) / `session_len` (LMDeploy) / `-c`/`ctx-size` (llama.cpp, Jan, oobabooga) / `num_ctx` (Ollama) / `contextLength` (LM Studio) / `--max-length` (MAX) / `context_window_size` (MLC) / `context_size` (LocalAI). Tensor parallel is `--tensor-parallel-size` (vLLM, alias `-tp`) / `--tp-size` (SGLang, alias `--tensor-parallel-size`, `--tp`) / `--tp_size` (TRT-LLM, alias `--tensor_parallel_size`) / `tp` (LMDeploy) / `--num-shard` (TGI) / `tensor_parallel_shards` (MLC) / `tensor_parallel_count` (Truss) / `tensor_parallel: true` (TabbyAPI) / `-sm tensor` (llama.cpp). Memory budget is `--gpu-memory-utilization` (vLLM) / `--mem-fraction-static` (SGLang) / `kv_cache_config.free_gpu_memory_fraction` (TRT-LLM) / `cache_max_entry_count` (LMDeploy) / `--device-memory-utilization` (MAX) / `gpu_memory_utilization` (MLC) — note these are *not* semantically identical (vLLM = whole-process budget incl. weights; SGLang = static pool for weights+KV; TRT-LLM = fraction of *free* memory after weights for KV; LMDeploy = fraction of free memory for KV).

## 6. Implications for Robotnik

- **The gap is real and unoccupied.** 11 engines and 21 platforms later: nobody ships a typed config that fans out to two engines. Every "multi-engine" platform is `enum backend` + raw passthrough. A canonical schema with per-engine emitters would be new, not a re-implementation.
- **Model the canonical schema on TRT-LLM's `LlmArgs` shape, not on vLLM's flag list.** It is the only engine that (a) is nested by concern (kv_cache_config / speculative_config / lora_config / scheduler_config / moe_config) and (b) tags fields `stable|beta|prototype`. Robotnik's schema should carry the same stability tags per (field, engine) pair.
- **Treat "engine + version" as the primary key.** vLLM shipped 18 minors in 12 months with removals in most of them; SGLang renames flags without aliases. Every emitter must be version-aware (`min_vllm_version`-style, as vLLM recipes do), and Robotnik should store a *rename ledger* per engine (e.g. vLLM `--guided-decoding-backend` → `--structured-outputs-config.backend` @0.12; `VLLM_ATTENTION_BACKEND` env → `--attention-backend` @0.13; SGLang `--enable-deepep-waterfill` → `--enable-waterfill` @0.5.16). No such ledger exists anywhere today; it is a differentiator on its own.
- **Do not pretend memory knobs are equivalent.** `gpu-memory-utilization` vs `mem-fraction-static` vs `free_gpu_memory_fraction` have different denominators. The canonical field should be an *outcome* (e.g. target KV-cache bytes or headroom) with engine-specific derivation, and the derivation should be checked against a benchmark, not assumed.
- **Parallelism needs a richer model than tp/pp/dp/ep integers.** SGLang's `--tp-size` changes meaning under `--enable-dp-attention`; TRT-LLM separates `moe_tensor_parallel_size` / `moe_expert_parallel_size` / `enable_attention_dp`; vLLM's `-ep` is a boolean; llama.cpp has split-mode instead. Use the vLLM-recipes *strategy* vocabulary (`single_node_tp`, `single_node_tep`, `single_node_dep`, `multi_node_tp_pp`, `pd_cluster`) as the canonical layer and let emitters expand it.
- **Always keep a validated passthrough.** Copy LocalAI: typed subset + `engine_args` map validated against the engine's real arg schema (vLLM `EngineArgs`, SGLang `ServerArgs`, TRT-LLM `LlmArgs` Pydantic) with did-you-mean errors. Robotnik can *load* those schemas from the pinned engine version at emit time rather than hard-coding them.
- **Emit each engine's native file, not a CLI string.** vLLM `--config` YAML (long flag names), SGLang `--config` YAML, TRT-LLM `--config` YAML (`LlmArgs`), llama-server `--models-preset` ini, TabbyAPI `config.yml`, Ollama Modelfile. Files diff and check in; CLI strings do not. (Dynamo already mounts SGLang's YAML from a ConfigMap — Robotnik output slots straight into DGD/KServe/llm-d `args`.)
- **Seed mappings from existing single-engine compilers and cross-engine corpora.** vLLM recipes (JSON API exists "for agent consumption"), sgl-cookbook generated YAML, NVIDIA deployment guides, and InferenceX's model × hardware × engine matrix give ground-truth (intent → flags) pairs for the same models on three engines.
- **Scope the first cut to vLLM + SGLang + TRT-LLM (PyTorch backend), with Aphrodite/Sonar as a vLLM dialect.** TGI is archived (migration source only); MLC-LLM is low-activity; MAX lacks a documented config-file format; llama.cpp/Ollama/TabbyAPI are a different (single-GPU, GGUF/EXL) vocabulary that could be a later "local" profile.
- **Benchmark-then-promote is the same loop everyone is converging on, but nobody has closed it.** vLLM `tools/recipes --generate-sweep`, Dynamo DGDR's profiler, GPUStack's derived flags all *suggest* a config; none records "config X on engine Y@version Z scored S, promoted". Robotnik's promotion record (canonical config + emitted native config + engine version + benchmark result) is the artefact that does not exist yet.
