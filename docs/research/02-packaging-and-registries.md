# 02 — Packaging formats and registries for inference serving: survey and diagnosis

*Research for Robotnik. Written 2026-09-03. Sources are inline; anything I could not confirm from a primary source is marked **[unverified]**. Star counts are as read from GitHub on 2026-09-03 and are approximate.*

## 0. Summary of the landscape

Every serious "package manager for models" falls into one of four camps, and none of them packages the thing Robotnik cares about (a verified, portable *serving configuration*):

| Camp | Unit of packaging | Carries serving config? | Hardware a dimension? | Examples |
|---|---|---|---|---|
| **Weight registries** | weights + descriptive metadata | No (only model-intrinsic facts: arch, context_length, chat template, quant) | No | HF Hub, GGUF, safetensors, ModelPack, Docker model-spec, KitOps, ORAS/Harbor |
| **Local runners with a registry** | weights + runtime defaults for ONE engine | Yes, but engine-locked and single-node (`num_ctx`, sampling, template) | Implicit ("does it fit in VRAM") | Ollama, LM Studio `model.yaml`, LocalAI gallery, Jan, Lemonade, Docker Model Runner, RamaLama |
| **Container-as-package** | container image + code + deps (+ optionally weights) | Yes, but as a vendor's runtime contract | Yes (accelerator enum / GPU SKU) | NIM, Cog, Truss, BentoML/OpenLLM, KAITO presets |
| **Recipes-in-git / operator templates** | YAML (engine flags keyed by model × GPU generation), or a Kubernetes CRD template | Yes — this is the only camp that does | Yes, explicitly | vLLM recipes, SGLang cookbook (archived), Dynamo recipes + AIConfigurator, llm-d guides, KServe `LLMInferenceServiceConfig`, Ray Serve `LLMConfig` |

The pattern: the moment a project includes serving config it is forced to key it by hardware and pin it to an engine version, and the moment it wants to be portable across engines it drops serving config entirely. Nothing has held both at once.

## 1. Survey

### 1.1 Hugging Face Hub

- **Unit:** a git repo of weights (safetensors preferred) plus `config.json`, tokenizer files, `generation_config.json`, `chat_template.jinja` and a `README.md` model card with YAML front-matter.
- **What the model card metadata carries** (per [hub docs](https://huggingface.co/docs/hub/en/model-cards)): `license`, `library_name`, `pipeline_tag`, `tags`, `base_model` (+ inferred relation `adapter|merge|quantized|finetune`), `datasets`, `language`, `new_version`, `model-index` eval results, CO2. **There is no field for serving configuration** — no TP, no context override, no engine, no hardware.
- **What `config.json` carries:** architecture identity. vLLM's [HF integration doc](https://docs.vllm.ai/en/latest/design/huggingface_integration/) says it reads `model_type` and `architectures` to pick a model class, then tokenizer + weights. `generation_config.json` supplies *default sampling params* — vLLM's `--generation-config` defaults to `auto` and loads it from the model path ([engine args](https://docs.vllm.ai/en/latest/configuration/engine_args/)); if it contains `max_new_tokens` that becomes a server-wide cap. So the Hub's "serving metadata" is: architecture, `max_position_embeddings`, `quantization_config`, dtype, and sampling defaults. Nothing about parallelism, memory, batching, or hardware.
- **Chat templates** moved out of `tokenizer_config.json` into a standalone `chat_template.jinja` (+ `additional_chat_templates/<name>.jinja`); transformers v5 writes only the new form ([docs](https://huggingface.co/docs/transformers/en/chat_templating_writing)). This is the one piece of *runtime-facing* config the Hub has actually standardised — and it took years and a breaking format change.
- **"Use this model" / local apps:** the model page generates per-app launch snippets (llama.cpp `llama-server -hf …`, `ollama run hf.co/…`, Jan, LM Studio, etc.) ([local-apps docs](https://huggingface.co/docs/hub/en/local-apps)). The snippets are templated from repo identity and GGUF quant file, not from any per-model serving hints. The Hub also has a GGUF metadata viewer and a JS parser (`@huggingface/gguf`) ([gguf docs](https://huggingface.co/docs/hub/en/gguf)).
- **Inference Providers:** a routing proxy to 18 partners (Baseten, Cerebras, Cohere, DeepInfra, Fal, Featherless, Fireworks, Groq, HF Inference, Novita, Nscale, OVH, Public AI, Replicate, Scaleway, Together, WaveSpeed, Z.ai) with `:fastest`/`:cheapest`/`:preferred` policies ([docs](https://huggingface.co/docs/inference-providers/index)). Mapping is provider-side; the Hub stores only "this provider serves this model id" ([hub integration](https://huggingface.co/docs/inference-providers/hub-integration)). `/v1/models` exposes per-provider pricing, context length, latency, throughput — i.e. the Hub knows *outcomes* of other people's serving configs, never the configs.
- **TGI**, HF's own engine, went to maintenance mode in March 2026 and redirects users to vLLM/SGLang/llama.cpp/MLX **[secondary sources: [datawookie](https://datawookie.dev/blog/2026-07-23-serving-hugging-face-models-locally/), [Spheron](https://www.spheron.network/blog/migrate-tgi-to-vllm-sglang-2026/)]**. HF now publishes distributions of vLLM/SGLang/llama.cpp rather than competing.
- **Adoption:** de facto universal identity space. Every recipe repo below keys recipes by HF repo path.
- **Why it didn't generalise into a serving package manager:** the Hub's schema is `transformers`' schema (`AutoConfig`). It describes what a model *is*, not how to run it; HF explicitly delegates "how to run" to third-party engines and providers.

### 1.2 GGUF and safetensors (file formats)

- **GGUF** ([spec](https://github.com/ggml-org/ggml/blob/master/docs/gguf.md)): single file = typed KV metadata + tensors. Standard keys: `general.architecture`, `general.name`, `general.file_type`, `general.license`, `general.base_model.*`, `[arch].context_length`, `[arch].embedding_length`, `[arch].block_count`, `[arch].rope.*`, `tokenizer.ggml.*`, `tokenizer.chat_template`. **No runtime keys** (threads, gpu layers, batch). It is the closest thing to a self-describing model package and it powers Ollama, LM Studio, llama.cpp, Jan, Lemonade, Docker MR — but only for the ggml family of engines. 45k+ public GGUF checkpoints on the Hub ([HF Ollama docs](https://huggingface.co/docs/hub/ollama)).
- **safetensors**: JSON header + tensors; `__metadata__` is a free-form string→string map ([docs](https://huggingface.co/docs/safetensors/metadata_parsing)). Stability's [ModelSpec](https://github.com/Stability-AI/ModelSpec) (v1.0.1, 71 stars) is the only attempt to standardise keys (`modelspec.architecture`, `implementation`, `title`, `usage_hint`, dtype hints) — descriptive only, negligible adoption. Serving config never went into the tensor file.

### 1.3 Ollama (registry + Modelfile)

- **Unit:** an OCI-style manifest of content-addressed blobs: `application/vnd.ollama.image.model` (GGUF weights), `.params` (JSON of sampling params + stop tokens), `.template` (chat template, optionally named), `.system`, `.adapter`, `.projector`, `.license` ([registry manifest](https://registry.ollama.ai/v2/library/llama3.2/manifests/1b), [pkg docs](https://pkg.go.dev/github.com/ollama/ollama/server/internal/manifest)). Layers dedupe across tags.
- **Modelfile** ([docs](https://docs.ollama.com/modelfile)): `FROM`, `PARAMETER`, `TEMPLATE`, `SYSTEM`, `ADAPTER`, `LICENSE`, `MESSAGE`, `REQUIRES` (minimum Ollama version — an engine-version constraint baked into the package). Documented `PARAMETER`s are `num_ctx` plus sampling (`temperature`, `top_k/p`, `min_p`, `repeat_*`, `seed`, `stop`, `num_predict`, `draft_num_predict`). `ollama create` can import safetensors (Llama/Mistral/Gemma/Phi3 families) or GGUF and `--quantize` at create time ([import docs](https://docs.ollama.com/import)).
- **Engines:** llama.cpp/ggml on CUDA/ROCm/Vulkan/Metal/CPU; since 2026 an **MLX engine** for safetensors models, default on macOS arm64, selectable elsewhere with `OLLAMA_MLX_BACKENDS` ([dev docs](https://docs.ollama.com/development); [yage.ai](https://yage.ai/share/mlx-apple-silicon-en-20260331.html) dates the switch to 2026-03-30). No vLLM. It also pulls straight from the Hub (`ollama run hf.co/org/repo:Q4_K_M`).
- **Hardware:** implicit. The package carries no hardware key; Ollama decides GPU offload at load time.
- **Adoption:** ~180k GitHub stars; $65M raise and ~9M users ([TechCrunch, 2026-07-09](https://techcrunch.com/2026/07/09/popular-open-source-ai-developer-tool-ollama-raises-65m-grows-to-nearly-9m-users/)). By far the most-used "model package manager".
- **Why it didn't generalise:** the package is the *Ollama runtime's* input, not an engine-neutral artifact. Parameters are llama.cpp's parameters; the registry is `ollama.com` (the registry server is not something you can self-host in the way you can an OCI registry — **[unverified]**); Docker/RamaLama had to build compatibility shims (`ollama://` transport) to read it. It solved single-node local, and it is the strongest evidence that a package manager *can* win when it fixes the engine and the hardware model to one box.

### 1.4 Docker Model Runner + Docker model-spec (2025–26)

- **Unit:** an OCI artifact. Config media type `application/vnd.docker.ai.model.config.v0.1+json`; layers `application/vnd.docker.ai.gguf.v3`, `.gguf.v3.lora`, `.gguf.v3.mmproj`, `.license`, `.chat.template.jinja` ([model-spec](https://github.com/docker/model-spec/blob/main/spec.md)). Config JSON: `config.format`, `config.gguf.{architecture,parameter_count,quantization}`, `config.size`, `descriptor.createdAt`, `files[]` ([config.md](https://github.com/docker/model-spec/blob/main/config.md)). Layers are always uncompressed, one raw file per layer, so engines can mmap them ([Docker blog, 2025-06-18](https://www.docker.com/blog/oci-artifacts-for-ai-model-packaging/)). Docker's stated rationale #4: "separate models from inference engines".
- **Packaging CLI** ([reference](https://docs.docker.com/reference/cli/docker/model/package/)): `--gguf`, `--safetensors-dir`, `--dduf`, `--mmproj`, `--license`, `--chat-template`, `--context-size`, `--format docker|cncf`, `--push`. So the artifact *can* carry a context size and a chat template — the only serving-adjacent knobs — and runtime tweaks happen out-of-band via `docker model configure --context-size 8192 ai/…` ([docs](https://docs.docker.com/ai/model-runner/)).
- **Engines:** llama.cpp (default, all platforms), vLLM (safetensors, NVIDIA Linux/WSL2; 0.19.1 pinned in `.versions`), diffusers ([repo](https://github.com/docker/model-runner)). Talked up at [FOSDEM 2026](https://fosdem.org/2026/schedule/event/VGXWNS-taming_the_llm_zoo_with_docker_model_runner_inference_with_oci_artifacts_llama_c/).
- **Interop:** August 2026 — DMR gained `docker model package --format=cncf` to emit ModelPack artifacts; participants Docker, Red Hat, Nutanix, Ant, Jozu ([CNCF blog, 2026-08-12](https://www.cncf.io/blog/2026/08/12/advancing-ai-model-interoperability-with-docker-and-modelpack/)).
- **Adoption:** ships in Docker Desktop; `ai/` namespace on Docker Hub; repo only ~640 stars.
- **Verdict:** a clean *weights-as-OCI* format. Serving config is deliberately not in scope beyond context size.

### 1.5 CNCF ModelPack (model-spec), modctl, KitOps/ModelKit, ORAS, Harbor/Zot

- **ModelPack** ([spec](https://github.com/modelpack/model-spec), 229 stars): config `application/vnd.cncf.model.config.v1+json`; layer types `weight`, `weight.config`, `doc`, `code`, `dataset` in `raw|tar|tar+gzip|tar+zstd`. Config schema ([config.md](https://github.com/modelpack/model-spec/blob/main/docs/config.md)): `descriptor{createdAt, authors, vendor, family, name, version, title, description, docURL, sourceURL, datasetsURL, revision, licenses}`, `config{architecture, format, paramSize, precision, quantization, capabilities{inputTypes, outputTypes, knowledgeCutoff, reasoning, toolUsage, reward, languages}}`, `modelfs{diffIds}`. **No runtime/engine/hardware field.** The spec's own use-case text says a platform must "identify the required server runtime (as well as startup parameters, necessary resources, etc.)" — and then provides no field for it. `modctl` CLI: 80 stars ([repo](https://github.com/modelpack/modctl)).
- **KitOps / ModelKit** ([repo](https://github.com/kitops-ml/kitops), 1.4k stars, v1.15.0 2026-06-25): Kitfile sections `package`, `model{name,path,framework,version,license,parts,parameters}`, `code`, `datasets`, `docs`, `prompts`, `mcpServers`. `parameters` is "an arbitrary section of yaml" ([format](https://kitops.org/docs/kitfile/format/)) — no hardware or engine fields. `kit dev start` serves a ModelKit locally (llama.cpp-based). Can now read/write ModelPack (`--use-model-pack`). Contributors named: Red Hat, PayPal, Ant Group, ByteDance; commercial home is Jozu Hub.
- **ORAS** is the generic push/pull primitive ([docs](https://oras.land/docs/how_to_guides/pushing_and_pulling/)); **Harbor** renders/labels model artifacts and positions itself as the model registry ([Harbor blog, 2026-03-11](https://goharbor.io/blog/cloud-native-ai-model-management/)); **Kubernetes image volumes** (mount an OCI artifact into a pod) went GA in v1.36 ([docs](https://kubernetes.io/docs/tasks/configure-pod-container/image-volumes/)), which is the consumption path ModelPack designed for. Red Hat's "modelcar" OCI model containers are the OpenShift AI flavour ([RHAI 3.4 docs](https://docs.redhat.com/en/documentation/red_hat_ai_inference/3.4/html/inference_serving_language_models_in_oci-compliant_model_containers/about-oci-models_oci-models)).
- The CNCF essay ["The weight of AI models: why infrastructure always arrives slowly"](https://www.cncf.io/blog/2026/03/27/the-weight-of-ai-models-why-infrastructure-always-arrives-slowly/) (Qi, Zhang, Zhou, 2026-03-27) frames the whole effort as *distribution* (versioning, RBAC, signing, P2P via Dragonfly) — the word "serving config" does not appear in its problem statement.
- **Verdict:** the OCI camp has (in 2026) converged on a shared answer to "how do I store and move weights through a container registry" and has explicitly scoped *out* "how do I run them".

### 1.6 RamaLama (Red Hat / containers org) — the closest multi-engine prior art

- **Unit:** two separate artifacts. (a) Models as OCI artifacts (GGUF/safetensors, `rlcr.io/ramalama/…`, tags like `:gguf`); (b) runtime images per engine × accelerator (`llamacpp-cuda-distroless`, `rocm`, `vulkan`, `intel`, `asahi`, `cann`, `musa`…), version-pinned to the RamaLama minor ([runtime docs](https://docs.ramalama.com/registry/artifacts/runtime), [repo](https://github.com/containers/ramalama), ~3.0k stars).
- **Engines:** `--runtime llamacpp|vllm|mlx` (MLX only with `--nocontainer`); whisper.cpp, OpenVINO, stable-diffusion mentioned. For vLLM the model is mounted read-only into the vLLM container; `ramalama convert` turns any source (`hf://`, `ollama://`, `modelscope://`, local) into an OCI image.
- **Serving config:** entirely CLI/`ramalama.conf`/env (`--ctx-size`, `--threads`, `--ngl`, `--runtime-args`, `--device`, `--backend`); precedence CLI > `ramalama.conf` > env > defaults ([serve man page](https://ramalama.ai/docs/commands/ramalama/serve/)). **The model artifact carries no serving config.** `--generate kube|quadlet|compose` emits deployment manifests from the *current* CLI state.
- **Hardware:** detected at run time to pick the runtime image; not a property of the model package.
- **Verdict:** RamaLama *is* a multi-engine, multi-accelerator launcher over OCI-packaged weights — but it achieves engine portability precisely by keeping config out of the package and re-deriving it per invocation. It is Robotnik's nearest prior art for the "engine × hardware image matrix" and a demonstration that the config layer was left as an exercise.

### 1.7 NVIDIA NIM — hardware-aware profiles

- **Unit:** a container per model (or the **model-free NIM** container that accepts any HF-format model at runtime and generates its manifest on startup, [docs](https://docs.nvidia.com/nim/large-language-models/latest/deployment/model-free-nim.html)).
- **Profile** ([2.x docs](https://docs.nvidia.com/nim/large-language-models/latest/deployment/model-profiles-and-selection.html)) = a pre-validated tuple `<backend>-<precision>-tp<N>-pp1[-lora]` (backend ∈ vLLM, SGLang, TensorRT-LLM; precision ∈ BF16/FP8/MXFP4/NVFP4), identified by a 64-char checksum so deployments can pin by hash. `list-model-profiles` buckets profiles into *compatible / low-memory (fits weights, not full context → suggests `--max-model-len`) / incompatible* against detected GPUs. Selection order: explicit `NIM_MODEL_PROFILE` → memory-aware selector (estimates weights + KV + activations) → manifest `profile_selection_criteria`; ties broken by TRT-LLM > vLLM, lower precision, latency > throughput, highest TP that fits. Backend CLI flags override profile values.
- **1.x** had *optimized* profiles tied to specific GPU device IDs (e.g. `tensorrt_llm-A100-fp16-tp1-throughput`, tagged `gpu`, `gpu_device 20b2:10de`), *generic* vLLM/SGLang profiles, and *local-build* TRT-LLM profiles compiled on the box ([1.12 docs](https://docs.nvidia.com/nim/large-language-models/1.12.0/profiles.html)). **2.x removed custom profile selectors** — you can only choose from the manifest. **3.0** (not NIM-certified; runs alongside 2.0) adds an opt-in Dynamo mode with separate frontend/router and vLLM workers ([release notes](https://docs.nvidia.com/nim/large-language-models/3.0.0/about-nim-llm/release-notes.html)).
- **Verdict:** the most complete *hardware-aware config bundle* in existence, and the clearest demonstration that the package is a (model × backend × precision × parallelism × GPU) tuple. It is also NVIDIA-only, closed-manifest, and its own profile model has been reshaped three times in ~2 years (custom → removed; per-device optimized → model-free generic; single container → Dynamo split).

### 1.8 Cog (Replicate), Truss (Baseten), BentoML / OpenLLM

- **Cog** ([yaml spec](https://cog.run/yaml/), ~9.5k stars): `build{gpu, cuda, python_version, python_packages, system_packages, run}`, `predict`, `train`, `concurrency`, `image`. Hardware = `gpu: true` + CUDA version; engine = whatever Python you write. Weights are not a first-class concept. It is a Dockerfile generator with an HTTP contract, aimed at arbitrary ML, not LLM serving.
- **Truss** ([config reference](https://docs.baseten.co/reference/truss-configuration), ~1.2k stars): `resources{accelerator, cpu, memory}` with an enumerated accelerator list `T4, L4, L40S, RTX_PRO_6000, A10G, V100, A100, A100_40GB, H100, H100_40GB, H200, B200, B300` (syntax `L4:4`); `trt_llm{build{checkpoint_repository, quantization_type fp8|fp8_kv|fp4…, tensor_parallel_count, max_seq_len, max_batch_size}, inference_stack v1|v2}`; `model_cache`; `docker_server`. Hardware IS a dimension and serving config IS in the package — but the `trt_llm` block is executed by Baseten's Engine Builder, so the package is portable only in the trivial (transformers/`model.py`) case.
- **BentoML** (~8.8k stars) / **OpenLLM** (~12.5k) / **openllm-models** ([repo](https://github.com/bentoml/openllm-models)): 40+ families, 100+ variants named `model:size-quant` (e.g. `qwen2.5:14b-instruct-awq`), each a `recipe.yaml` with `service_config{resources: gpu, gpu_type, memory}`, `envs`, `extra_requirements`, `engine_config` (vLLM args). This is a genuine model × GPU-type × vLLM-args catalogue — maintained by one vendor, for one engine, consumed by `openllm serve`.
- **Verdict:** all three prove that a per-model, per-accelerator serving config *can* be written down; all three keep it inside a vendor's deployment contract.

### 1.9 MLflow / MLServer / Seldon

- MLflow's registry versions a `MLmodel` folder with "flavors" (pyfunc etc.); Seldon's prepackaged MLflow server runs it on **MLServer**, whose `model-settings.json` (`name`, `implementation`, `parameters{uri, version, extra}`, `parallel_workers`, batching) sits next to the artifacts ([MLServer docs](https://mlserver.readthedocs.io/en/latest/reference/model-settings.html)). Seldon Core 2 added `spec.llm` on its Model CRD and an LLM Module with vLLM/DeepSpeed/HF runtimes ([Seldon](https://www.seldon.io/introducing-seldon-llm-module-for-deploying-and-managing-genenerative-ai/)). Classic-ML lineage; LLM serving bolted on. No hardware dimension in the artifact.

### 1.10 Xinference, LocalAI, LM Studio `model.yaml`, Jan, Lemonade, Nexa/GenieX, llamafile

- **Xinference** ([repo](https://github.com/xorbitsai/inference), ~9.5k stars, v3.0.0): built-in and custom model JSON: `model_name`, `model_family`, `model_ability`, `chat_template`, `stop`, `model_specs[]{model_format pytorch|ggufv2|gptq|awq|mlx, model_size_in_billions, quantizations, model_id|model_uri}` ([custom models](https://inference.readthedocs.io/en/stable/models/custom.html)). Engine (`model_engine` = vLLM/SGLang/llama.cpp/transformers/TensorRT) is a *launch* parameter, not part of the registration. No hardware field.
- **LocalAI** ([repo](https://github.com/mudler/LocalAI), ~48.8k stars, v4.3.0 May 2026): gallery YAML per model: `backend`, `model`, `threads`, `context_size`, `gpu_layers`, `f16`, `flash_attention`, templates ([gallery](https://localai.io/models/index.html)). Backends (llama.cpp, vLLM, transformers, diffusers, whisper, MLX, SGLang, …) are themselves pulled as OCI images from a "backend gallery". The most engine-diverse local registry; config is per-backend and per-file, single-node.
- **LM Studio `model.yaml`** ([spec](https://github.com/modelyaml/modelyaml), 64 stars, "First Draft v1.0"; [LM Studio docs](https://lmstudio.ai/docs/app/modelyaml); [Willison, 2025-06-21](https://simonwillison.net/2025/Jun/21/model-yaml/)): `model: org/name`, `base[]` (concrete GGUF/MLX sources), `metadataOverrides{minMemoryUsageBytes, architectures, domain, trainedForToolUse, vision}`, `config{load.contextLength, operation.*}`, `customFields` with effects like `setJinjaVariable` (e.g. `enableThinking`), `suggestions`. Explicitly a "virtual model" that abstracts GGUF vs MLX. Only implementer: LM Studio.
- **Jan** used Cortex's `model.yml` (paths, `ngl`, `ctx_len`, engine, prompt template) and is deprecating Cortex for direct llama.cpp ([issue #4941](https://github.com/janhq/jan/issues/4941)).
- **Lemonade (AMD)** ([repo](https://github.com/lemonade-sdk/lemonade), ~5.6k stars; [Phoronix on 11.0](https://www.phoronix.com/news/AMD-Lemonade-11.0)): the model list keys each entry by a `recipe` (`llamacpp`, `flm`, `vllm`, `ds4`, `ryzenai-llm`, OGA variants) that maps to a hardware path (XDNA2 NPU, Radeon, CUDA, Metal, CPU). Hardware is effectively a dimension of the model *name*. **[The exact manifest schema page 404'd; recipe list read from the README.]**
- **Nexa SDK** now presents on GitHub as **GenieX**, "the community version of Qualcomm GENIE", ~8.3k stars, llama.cpp + Qualcomm AI Engine Direct runtimes, models from HF (GGUF) or Qualcomm AI Hub (chipset-specific compiled bundles) ([repo](https://github.com/qualcomm/nexa-sdk)). **[Nexa → Qualcomm corporate relationship unverified.]** Notable because the NPU path packages *compiled, chipset-specific* bundles — hardware baked into the artifact.
- **llamafile** ([repo](https://github.com/mozilla-ai/llamafile), ~25.9k stars, 0.10.x under Mozilla.ai): weights + llama.cpp + Cosmopolitan libc in one executable. The extreme of "package = engine + weights"; portable across OSes precisely because it fixes the engine.

### 1.11 InstructLab

Not a packaging project. The core repo was archived 2026-04-23 and split into SDG Hub and Training Hub ([repo](https://github.com/instructlab/instructlab)). Its 2024 packaging story was "use KitOps" ([Red Hat, 2024-09](https://developers.redhat.com/articles/2024/09/16/enhance-llms-instructlab-kitops)).

### 1.12 Engine-native recipe repositories (vLLM, SGLang, Dynamo, MAX)

- **vLLM recipes** ([repo](https://github.com/vllm-project/recipes), ~1.0k stars / 400 forks; [site](https://recipes.vllm.ai/), 187 recipes). Since mid-2026 a *structured YAML per HF repo* (`models/<hf_org>/<hf_repo>.yaml`) rendered as an interactive command builder and exported as JSON (`/models.json`) "for agents/tools". Schema ([CONTRIBUTING](https://github.com/vllm-project/recipes/blob/main/CONTRIBUTING.md)): `meta{…, hardware: {h200: verified, …}}`, `model{model_id, min_vllm_version, docker_image (per brand), nightly_required, architecture dense|moe, context_length, base_args, base_env}`, `variants{default, …}{precision, vram_minimum_gb, extra_args, hardware_overrides{blackwell|amd|…: {extra_args, extra_env}}}`, `features{tool_calling, reasoning, spec_decoding}`, `strategies{single_node_tp, single_node_tep/dep, multi_node_*, pd_cluster}`. VRAM formula `ceil(params × bytes_per_param × 1.2)`. A converter emits `config.yml` for `vllm serve --config` plus `env.sh`. Hardware options: H100/H200/B200/B300, GB, MI300X/MI325X/MI355X. **This is the most Robotnik-shaped artifact that exists** — and it is engine-specific, version-pinned (`min_vllm_version`, `nightly_required`), community-maintained YAML in git with a "verified on" map rather than a test matrix.
- **SGLang cookbook** ([repo](https://github.com/sgl-project/sgl-cookbook)): human-edited YAML under `data/models/src/<sglang-version>/`, compiled to schema-complete YAML under `generated/<version>/`, plus per-model React `ConfigGenerator` components with hardware overrides (H100/H200/B200/MI300) and quant overrides ([CLAUDE.md](https://github.com/sgl-project/sgl-cookbook/blob/main/CLAUDE.md)). **Archived 2026-06-11 (10 stars) and folded into `sglang/docs_new`.** Configs were versioned by engine release because they did not survive engine upgrades.
- **NVIDIA Dynamo recipes** ([README](https://github.com/ai-dynamo/dynamo/blob/main/recipes/README.md)): layout `<model>/<framework vllm|sglang|trtllm>/<agg|disagg>/deploy.yaml` (+ `perf.yaml`, `model-cache/`), covering H100/H200/A100/B200/GB200/GB300. Paired with **AIConfigurator** ([repo](https://github.com/ai-dynamo/aiconfigurator), 437 stars): inputs model + GPU count/SKU + backend + SLA, *simulates* GEMM/attention/comm to rank TP/PP/DP × replicas × agg-vs-disagg, and emits Dynamo manifests or llm-d Helm values. I.e. NVIDIA's answer to "which config?" is a *solver*, not a registry.
- **Modular MAX**: `max serve --model <hf id>` with `--quantization-encoding`, `--devices`, `--max-length`, `--max-batch-size`, `--device-memory-utilization`, `--data-parallel-degree`, `--config-file`; `max-recipes` are application examples ([CLI](https://max.modular.com/cli/serve/)). Uses the HF repo as the model registry; no serving-config registry.

### 1.13 Kubernetes: WG Serving, Gateway API Inference Extension, LeaderWorkerSet, inference-perf, KServe, llm-d, KAITO, Ray

- **WG Serving concluded and disbanded in Feb 2026** ([CNCF](https://www.cncf.io/blog/2026/02/26/kubernetes-wg-serving-concludes-following-successful-advancement-of-ai-inference-support/)). Deliverables: Gateway API Inference Extension (→ SIG Network), LeaderWorkerSet (→ SIG Apps), inference-perf + the "Serving Catalog" (→ SIG Scalability), AI conformance, DRA input. **It never attempted a model-packaging or serving-config standard**; the post says llm-d and AIBrix are the "more appropriate forums".
- **Gateway API Inference Extension** ([repo](https://github.com/kubernetes-sigs/gateway-api-inference-extension), GA): `InferencePool` (a set of model-server pods + endpoint picker) and `InferenceObjective` (per-request priority/criticality). It standardises *routing to* a pool, not *what runs in* the pool. The Endpoint Picker is being consolidated into the llm-d scheduler (April 2026 newsletter, [InferenceOps](https://inferenceops.substack.com/p/state-of-the-model-serving-communities-b93)).
- **KServe v0.17** made `LLMInferenceService` production-ready (built on llm-d; spec has `model{uri hf://…|s3|pvc}`, `template|worker|prefill`, `router`, `parallelism{tp,dp,ep}`, `replicas`) with composable `LLMInferenceServiceConfig` templates ([overview](https://kserve.github.io/website/docs/model-serving/generative-inference/llmisvc/llmisvc-overview), [release](https://kserve.github.io/website/blog/kserve-0.17-release)). The "package" is a CRD template, not an artifact.
- **llm-d** (CNCF Sandbox March 2026, ~4.4k stars, v0.7 May 2026): "well-lit paths" are guides packaged as Kustomize with a machine-readable `guide.yaml` and Components per accelerator (GPU/vLLM, AMD, TPU, XPU) ([guides](https://github.com/llm-d/llm-d/blob/main/guides/README.md)). Per-model vLLM args are left to each guide.
- **KAITO** (~1.0k stars, v0.12.0 2026-08-21): ~60 curated presets plus, since v0.9.0, any vLLM-supported HF model; the controller "retrieves the model metadata from the Hugging Face website and generates model preset configurations", estimates GPU memory from instance type + metadata, and picks TP/PP/max-model-len for you ([presets](https://kaito-project.github.io/kaito/docs/presets), [repo](https://github.com/kaito-project/kaito)).
- **Ray Serve LLM** `LLMConfig{model_loading_config, accelerator_type: A10G|L4|…, engine_kwargs{tensor_parallel_size, max_model_len…}, deployment_config}` ([docs](https://docs.ray.io/en/latest/serve/api/doc/ray.serve.llm.LLMConfig.html)) — again hardware + engine kwargs side by side, in the deployment object.
- **Verdict:** Kubernetes standardised the *scheduling* and *routing* envelope (LWS, InferencePool, DRA) and left model × engine × hardware config to operators, each of which grew its own preset/template system.

## 3. Diagnosis: why is there no centralised package manager for inference serving?

### H1 — The package is really (model × engine × engine-version × hardware × config), and hardware breaks portability. **Strongly supported.**

Every project that put serving config in the package was forced to add hardware as a key: NIM profiles are literally named `<backend>-<precision>-tp<N>` and, in 1.x, tagged with a GPU device ID; vLLM recipes have `hardware_overrides{blackwell, amd}` and a `hardware: {h200: verified}` map; SGLang cookbook had per-hardware TP/DP/EP overrides; Dynamo recipes are directories per SKU; Truss enumerates 13 accelerators; Ray has `accelerator_type`; Lemonade keys recipes by NPU/GPU path; KAITO derives config from instance type. Conversely every project that wanted portability (HF, GGUF, ModelPack, Docker model-spec, KitOps) left serving config out. Nobody has published a format that carries config *and* is hardware-neutral, because the values (`tp`, `max-model-len`, `gpu-memory-utilization`, kernel/attention backend, quant format) are not hardware-neutral. npm works because `x86_64-linux` is one of ~6 targets and the artifact is the same bytes on all of them; here the "target triple" is (GPU SKU × count × interconnect × driver × engine build), and the artifact *contents* change per target.

### H2 — Weights are huge, so registries optimised for blobs and ignored config. **Supported, and it explains the OCI camp precisely.**

The OCI/ModelPack work is explicitly motivated by moving tens-of-GB to TB artifacts through registries with dedupe, signing, P2P (Dragonfly), and mounting via image volumes (CNCF essay; Harbor blog; Docker's "uncompressed single-file layers so engines can mmap"). Config is a few hundred bytes and cannot justify a spec; ModelPack's own text acknowledges runtimes need "startup parameters, necessary resources" and then defines no field. The blob problem is real and now largely solved; it absorbed the standards energy that might otherwise have gone to config.

### H3 — Engine flag surfaces churn too fast to be a stable target. **Supported.**

vLLM documents roughly 200–250 engine arguments across a dozen config classes; recipes need `min_vllm_version` and `nightly_required` because flags appear and disappear between releases. The SGLang cookbook versioned its YAML by engine release (`src/v0.5.6`, `v0.5.8`) and was archived within months, folded back into the engine's docs. NIM dropped user-defined profiles between 1.x and 2.x and restructured again for 3.0. Jan is ripping out Cortex; Ollama swapped its Apple backend to MLX; TGI went to maintenance. HF's Inference Endpoints and NIM both now ship the *engine* as the unit of stability (a pinned container) and treat flags as ephemeral. A cross-engine config schema would have to be re-derived every release of every engine — which is exactly what a recipes repo does, by hand.

### H4 — Vendor incentives favour lock-in. **Partially supported; explains why vendor packages don't generalise, not why no neutral one exists.**

NIM's profile hashes point at NVIDIA-built engines; Truss's `trt_llm` block is executed by Baseten's Engine Builder; OpenLLM recipes are BentoML's; Ollama's registry is Ollama's. Each vendor's package is a contract with that vendor's runtime, so none can be the neutral one. But the counter-evidence matters: Docker, Red Hat, Ant, Nutanix and Jozu *did* converge on ModelPack in 2026, and HF opened "Use this model" to every local app. Vendors cooperate readily on the neutral part (weights); they simply have no incentive to donate the part they monetise (tuned configs per hardware), because that is their benchmark advantage.

### H5 — Kubernetes operators absorbed the problem. **Supported.**

WG Serving explicitly closed without a packaging standard and pointed at llm-d/AIBrix. KServe (`LLMInferenceServiceConfig`), llm-d (`guide.yaml` + accelerator Components), KAITO (generated presets), Dynamo (recipes + AIConfigurator), Ray (`LLMConfig`) and Seldon (`spec.llm`) each own a template/preset system. The "package" became a CRD or Helm values file that lives *inside the operator's release cycle*, so it is versioned with the operator, not with the model, and is not shareable across operators. This is where the config actually lives in production in 2026.

### H6 — The people who need it just keep YAML in git. **Supported — and the successful "registries" are literally that.**

vLLM recipes is 187 YAML files in a GitHub repo with a JSON export; Dynamo recipes are YAML in the Dynamo repo; llm-d guides are Kustomize in git; SGLang's cookbook went back into the docs tree; openllm-models is YAML per model. The de facto package manager for serving config is *GitHub plus an HF repo id as the primary key*. Nobody has been forced to build a resolver because the consumer is a platform engineer with a text editor, not a build system.

### H7 — Other things the evidence suggests.

1. **Config is increasingly derived, not authored.** NIM's memory-aware selector, KAITO's memory estimation, AIConfigurator's simulation, vLLM recipes' `vram_minimum_gb` formula, Ollama's automatic GPU offload: the trend is `f(model, hardware, SLA) → config`. A static registry can't hold a function; a solver can. The most credible 2026 answers to "which config?" (AIConfigurator, NIM auto-select) are solvers.
2. **Verification is the scarce resource, not the schema.** npm scales because tests run on any laptop. A serving config is only known-good on the GPU it was run on, and GPU-hours are expensive, so coverage is a sparse `verified` map (vLLM recipes) or vendor-funded (NIM "certified" profiles; NIM 3.0 is explicitly "not certified"). Without a cheap verification oracle a community registry can't accumulate trust.
3. **Local vs datacenter is a real fork.** Where the hardware dimension collapses to one box ("does it fit in VRAM?"), package managers *did* win: Ollama, LM Studio, Docker MR, RamaLama. Where it expands to TP/PP/DP/EP/disaggregation across nodes, nothing has. Robotnik's problem is the second one.
4. **Model identity is unstable below the HF repo.** Quantised forks (unsloth/bartowski GGUFs, AWQ/FP8 re-uploads) create new identities per precision; recipes handle this with `variants[].model_id`. A config registry has to key on (base model, precision, checkpoint) not "the model".

**Net:** H1 + H3 + H7.1/7.2 are the structural causes; H2, H5, H6 describe where the energy went instead; H4 is real but secondary.

## 4. Implications for Robotnik

- **Do not build a registry of configs; build a resolver over a sparse, versioned evidence base.** The winning shape in 2026 is `f(model, engine@version, hardware, SLA) → config`, with recorded verifications as inputs (AIConfigurator + vLLM recipes' `verified` map are the two halves nobody has joined).
- **Adopt the existing primary keys rather than inventing identity:** HF repo path (+ revision) for the model, engine name + semver for the runtime, and a hardware tuple (SKU × count × interconnect) modelled the way NIM and vLLM recipes already do it.
- **Treat vLLM recipes' YAML schema as the closest prior art and be a superset of it** (`base_args`/`base_env`, `variants` with `hardware_overrides`, `strategies`, `min_engine_version`). It already exports JSON for agents; Robotnik can ingest it on day one and contribute back.
- **Make engine-version the first-class dimension, not an afterthought.** The SGLang cookbook died because configs were pinned per release with no migration story; "port config from vLLM 0.17 → 0.19" and "vLLM → SGLang" are the same operation Robotnik should own.
- **Separate model-intrinsic facts from deployment decisions,** and source the former from files that already exist (`config.json`, `generation_config.json`, `chat_template.jinja`, GGUF KV, ModelPack `config`) instead of re-declaring them.
- **Emit into the places config actually lives:** `vllm serve --config` YAML, SGLang CLI, KServe `LLMInferenceServiceConfig`, llm-d `guide.yaml`/Helm values, Dynamo DGD, Ray `LLMConfig`, RamaLama `--generate kube`. Robotnik's output is a compiler target list, not a new runtime.
- **Expect hardware-neutral portability to be a fiction; sell explicit translation with confidence levels** (verified on / estimated for / unknown), because the evidence says every honest system ended up with a per-SKU matrix.
- **Attach a cheap verification oracle** (smoke-load + short benchmark that writes back a `verified` record) — that is the missing piece that would let a community evidence base compound the way npm's test suites do.
- **Package weights via OCI/ModelPack when you need to move them; don't try to put serving config in the artifact.** The OCI camp has explicitly scoped it out and that boundary is now shared by Docker, Red Hat, Ant and CNCF.
- **Watch NIM 3.0 / Dynamo and llm-d as the two places a de facto standard could still emerge from** (NVIDIA-led solver + manifest vs. CNCF-led CRD templates); position Robotnik as the vendor-neutral layer that reads and writes both rather than a third competitor.
