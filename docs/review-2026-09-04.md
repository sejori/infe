## 2. Correctness defects that break parity (must fix before any perf claim)

Verified with a CPU-only probe inside the vLLM 0.28 image, feeding identical text to the stock `hermes`
parser and to `infe_hermes` via the shim:

```
non-streaming
  hermes      calls=[('get_weather', '{"city": "London", "units": "celsius"}', id=True)]
  infe_hermes calls=[('get_weather', '{"name": "get_weather", "arguments": {"city": "London", "units": "celsius"}}', id=True)]
streaming (per-token chunks, accumulated by index)
  hermes      {0: ('get_weather', '{"city": "London"}', id=True)}
  infe_hermes {0: ('get_weather', '\n{"name": "get_weather", "arguments": {"city": "London"}}\n\n{"name": ... "London"}}\n', id=False)}
```

1. **`arguments` is the whole tool-call object, not the `arguments` sub-object.** `HermesParser::extract_name`
   returns `(name, json_str.to_string())` — the full JSON. Both shims then `json.loads` that and re-serialise
   the wrapper as `function.arguments`. Any client that calls the tool receives `{"name":…, "arguments":{…}}`
   as its arguments.
2. **Streaming re-sends the whole buffer on completion.** Fragments are emitted as they arrive (raw, including the
   `{"name":` prefix), and then the `is_complete` delta carries `arguments_buffer` again → arguments duplicated.
   Stock vLLM streams only the *diff* of the arguments object (`args_diff` in `hermes_tool_parser.py`).
3. **No tool-call id is ever generated.** `ToolCallArgState.id` is declared but never assigned in any dialect;
   the shim only passes an id if Rust provides one. Stock vLLM calls `make_tool_call_id()` on the first delta.
   OpenAI clients key tool results on that id.
4. **Reasoning dialect is registered as a tool parser.** vLLM and SGLang both have a separate reasoning-parser
   interface (`--reasoning-parser`; vLLM `vllm.reasoning`, SGLang `ReasoningParser.DetectorMap`). Registering
   `infe_deepseek_reasoning` in the *tool* registry means it is never used for reasoning.
5. SGLang shim: `ToolCallItem.parameters` gets the same wrapper JSON; `tool_index` lookups by name work only
   once `name` has been extracted, which for this dialect happens at the close marker, so no incremental
   argument deltas are attributable to a tool during the stream.

## 3. Other review findings

- **Conformance is weaker than the brief requires.** Six fixtures, all `source: synthetic`; none mined from either
  engine's test suite. `expected_tool_calls[].arguments` is `null` in the fixtures, so the runner skips the argument
  assertion (which is why defect #1 passes CI). Content is checked with `contains`, not equality.
- **`infe-core` is dead weight for this milestone.** ~1,000 lines (step contract, DLPack buffer views with `unsafe`,
  manifest types) and `infe-parsers` does not reference a single symbol from it (`grep infe_core` → nothing).
  It is a dependency in `Cargo.toml` only. Fine as a placeholder, but it should not be described as used.
- **`registry/` does not exist**; no `manifest.yaml` for the component (BRIEF §5.2).
- **Naming hazard.** `shims/vllm/infe_parsers/__init__.py` is a package literally named `infe_parsers` that does
  `from infe_parsers import StreamingParser`. Loaded via `--tool-parser-plugin <path>` it works only because vLLM
  imports it under the file stem `__init__`; anywhere on `sys.path` it shadows the real wheel. Rename to
  `infe_parsers_vllm` or move under `infe_parsers/shims/vllm/` inside the wheel (which is what the docstring claims).
- **README claim "both engines call their parsers per token" is true** for vLLM (chat serving calls
  `extract_tool_calls_streaming` per delta) and SGLang (`parse_streaming_increment` per delta) — but the shim
  does exactly the same: one PyO3 call per delta with a Python dict allocated per call. There is no batching at
  the engine seam, so the brief's boundary rule (§5.1) is not actually exercised by M1. That is acceptable for
  parsers (the seam is per-delta by design) but the README should not claim otherwise.
- **CI** runs fmt/clippy/test/criterion; no wheel build, no conformance against a pinned engine, no nightly drift.
- **Committed results** (`bench/results/*_ab.json`, 3 × 3,551 lines) are the toy comparison and should be
  deleted or clearly labelled; they would mislead anyone reading the repo.
- Positives: workspace builds clean on Rust 1.98 with pedantic clippy; abi3 wheel builds first time; the vLLM
  registration path (`ToolParserManager.register_module`) is the right one and is honoured by 0.28's new
  `ParserManager` layer; the SGLang `ToolCallParserEnum` injection works and the CLI accepts `infe_hermes`.

### How to read this — the headline deltas are artefacts, not wins

- **Parity fails on every infe request.** `args_ok = 0` across the board (defects #1/#2), `has_id = 0` on vLLM
  (defect #3), and `calls` is exactly half of stock on both engines: the Rust state machine never assigns
  `state.index`, so the second `<tool_call>` is emitted with index 0 and clients merge it into the first
  (defect #6). A client using these deltas would call `get_time` with the concatenated arguments of both calls.
- **vLLM infe's lower ITL p99 (−80 %) and TTFT (−30…−54 %) come from emitting twice as many chunks.** Stock
  Hermes deliberately withholds deltas until it can parse a valid partial-JSON prefix and then emits *argument
  diffs*; that buffering is where the 58–100 ms p99 spikes come from. infe forwards every raw fragment
  immediately, including `{"name": "…", "arguments":`, and so has nothing to wait for. Same reason `chunks/s`
  doubles. This is a semantic difference, not a CPU saving.
- **SGLang infe's lower ITL p99 (−85 %) and *higher* TTFT (+35…+142 %) come from the opposite artefact.** The shim
  can't attribute fragments to a tool until the name is known, which for this dialect is at the close marker, so
  it emits a single delta per tool call. Fewer chunks → tiny p99; first chunk only when the first call
  completes → TTFT balloons.
- **End-to-end latency is unchanged or slightly worse** (+0.1 … +5.4 %), as expected: generation is GPU-bound and
  parsing is not on that path.
- **Conclusion: no evidence yet that the Rust parser improves anything.** The measurable cost in the stock
  parsers is the partial-JSON parse + diff per delta. A Rust parser that implements *the same* semantics
  (incremental arguments diff, id on first delta, index per call) is the thing to benchmark; the current one
  does less work and different work, so its numbers cannot be compared.

## 5. Recommended next steps, in order

1. Fix the Rust dialect semantics: emit `id` on first delta, assign `index` per call, extract the `arguments`
   sub-object and stream its *diff* (match vLLM's `hermes_tool_parser.py` and SGLang's `HermesDetector`
   behaviour exactly), reset state after `</tool_call>`. Add fixtures with `arguments` set and with two calls.
2. Fold the three shim fixes in (import fallback, `tool_calls=[]`, SGLang `structure_info`), rename the shim
   packages so they cannot shadow the wheel, and register the reasoning dialect via the reasoning-parser
   interfaces rather than the tool registry.
3. Mine conformance fixtures from `vllm/tests/tool_use` + `tests/entrypoints/openai/tool_parsers` and
   `sglang/test/.../function_call` as the brief requires; make the runner assert arguments and content equality.
4. Commit the client, driver, launcher and aggregator under `bench/harness/`; add a maturin wheel job and a
   conformance-vs-pinned-engine job to CI; delete or relabel the toy `bench/results/*_ab.json`.
5. Re-run this exact protocol (same images, model, GPU, rounds). Only then is a perf claim admissible. Expect the
   honest result to be "parity + no regression" rather than a large win; the win, if any, will be at 256+ streams
   in API-server CPU, which needs a proper sampler (psutil on the container pid, 1 s cadence), not docker stats.

## Reading

1. **vLLM: full output parity, every counter.** Two calls per request, valid argument objects, ids, names.
2. **SGLang: parity on what it emits, but only one call per request.** Raw SSE from a live server shows why:
   for this prompt Qwen2.5 under SGLang's chat template emits the *second* call as bare JSON with **no
   `<tool_call>` opener** (`</tool_call>\n{"name": "get_time", …}}\n}`), plus a stray `}`. Stock `qwen25`
   (SGLang) and `hermes` (vLLM) both tolerate marker-less continuation calls; the Rust Hermes dialect does not,
   so the second call is streamed as `content` (56 chars/request). **Defect #7.** Note vLLM's rendering of the
   same prompt did include both markers, which is why vLLM shows 2 calls; this is template/model behaviour the
   dialect must absorb, exactly as the stock parsers do.
3. **The Rust parser does not stream argument fragments.** `hermes.rs` says so in a comment ("We don't emit
   intermediate argument deltas … At completion, we emit the extracted sub-object as a single diff"). Stock
   parsers emit name first, then argument diffs as partial JSON becomes valid (9–20 deltas per call). Effects:
   vLLM infe ITL p50 is **10× worse** (52 ms vs 5.3 ms — the "inter-token" gap is now the gap between one
   completion delta and the next), TTFT is +70…+140 % on both engines (first delta waits for the first call to
   finish), chunks/s collapses. The manifest's `parity.streaming_diff: true` is wrong. **B2 is not done.**
4. **SGLang infe's better ITL p99 (−82…−87 %) and vLLM infe's e2e −10 % at 256 are the same artefact** (fewer,
   larger deltas; and e2e is within IQR). No CPU-side claim can be made from this round either.
5. Minor: infe ids are deterministic per index (`call_aaaaaaaa` for every request's first call). Unique within a
   message, which is what the API requires, but clients that key on ids across a conversation will collide.
   Arguments are re-serialised without spaces (JSON-equal, not byte-equal).

## Verdict

Correctness: vLLM at parity; SGLang blocked by defect #7. Performance: not measurable until B2 (incremental
argument streaming with partial-JSON validation) is implemented, because emission granularity dominates every
latency metric. The stock parsers' cost that Rust is meant to remove *is* that partial-JSON work — so B2 is both
the parity requirement and the only place a real win could show up.

## Reading

1. **vLLM: full parity, at all three levels.** `calls`, `args_ok`, `has_id`, `name` all equal stock exactly
   (1536/1536 at conc 256). This is the first round where an infe arm is output-correct end to end.
2. **vLLM latency is now flat-to-better, with no parity cost.** ITL p99 −18.4 % @8 and −19.1 % @64 have
   non-overlapping IQRs (58.14 ±0.42 → 47.45 ±0.44; 62.66 ±3.87 → 50.71 ±0.68) and are the most robust signal
   in the set. TTFT −1.5/−6.4/−14.5 % and e2e −0.4/−4.3/+1.6 % all have overlapping IQRs — treat as "no
   regression", not as wins.
3. **Caveat that blocks a CPU claim: infe emits more deltas than stock** (173 vs 157 per 8 requests; 5589 vs
   4732 at conc 256; chunks/s +15 % → +34 %). More chunks in the same wall-clock time mechanically shrinks the
   inter-token gap, so part of the ITL p99 improvement is granularity, not saved CPU. e2e being flat confirms
   generation is GPU-bound and unaffected either way. **A CPU-saving claim still needs the 1 s psutil sampler on
   the API-server pid (task D4); docker stats at 2 samples/run cannot support one.**
4. **SGLang regressed and is now the outlier.** ITL p99 is 90–98 % *worse* and only 2 deltas per call are
   emitted (vs ~5 stock). Cause is in the shim, not the Rust: `parse_streaming_increment` has
   `elif name:` guarding the fragment path, so now that B2 emits the name only on the *first* delta, every
   subsequent nameless argument fragment is silently dropped; the completion delta then carries the whole
   remainder. **Defect #8** — the shim must forward nameless fragments with `name=None` (SGLang's own
   `_process_tool_call_stream` already handles `call_item.name is None` as "argument delta").
5. **Defect #7 (marker-less continuation) is still open** — SGLang infe still reports 1 call per request against
   stock's 2 (768 vs 1536 at conc 256), because Qwen2.5 under SGLang's template emits the second call as bare
   JSON with no `<tool_call>` opener.
6. Defect #B7 (index-derived ids) is still open; ids remain deterministic per index.

## Verdict

**vLLM: parity reached, no regression, ITL p99 improved.** That satisfies the BRIEF's acceptance criteria (1),
(2) and (4) for that engine; criterion (3) — a defended CPU-side improvement — is not yet supported because the
delta-count confound and the missing CPU sampler both remain. **SGLang: blocked on defects #7 and #8**, both in
the shim, both small.
